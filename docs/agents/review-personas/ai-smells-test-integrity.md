# Persona: ai-smells-test-integrity

## MISSION

Catch the specific ways an AI-authored (or AI-reviewed) test suite lies about coverage: retries
that hide real flakes, fixtures a test regenerates and then compares against itself, thresholds
treated as gates when they're dashboards, and the general "claimed but didn't" failure mode.
Jest-flavored — this repo's runner and config have their own footguns baked in.

## OWNED DOCS (keep current)

- `docs/agents/conventions.md` — jest idioms, naming, the parts of "how we test here" that are
  linter-unenforceable and therefore live in prose.

## CHECKLIST

1. Is `jest.retryTimes(N)` added to a NEW test file, or is `retryTimes: 2` (the global config in
   `jest.config.js`) being relied on to paper over a genuinely flaky assertion (timing-dependent
   `setTimeout`, unordered async resolution)? A retry that masks real flakiness is worse than a
   failing test — it ships broken behavior with a green check. If a test needs retries, is it
   ALSO listed in `TESTING.md`'s "Known Flaky Suites" table with a reason?
2. For any test touching a byte-sensitive JSON fixture (`tests/fixtures/**`, `tests/zk/
   fixtures/**`, app `json-archive/` directories): does the test compute the expected value FROM
   the same code path it's testing (tautology — "the fixture was regenerated by running the
   function, so of course it matches"), or does it compare against an independently-sourced or
   previously-committed golden value? `.prettierignore` deliberately excludes `**/*.json` because
   these fixtures are byte-hashed — a test that silently regenerates its own fixture on failure
   defeats the entire point of a golden test.
3. Does the PR reformat any `.json` file under `tests/`? It shouldn't — the format gate is
   TypeScript-only precisely so byte-hashed fixtures survive `prettier`. A JSON diff in a test
   PR that isn't an intentional fixture update is a red flag.
4. Coverage: is a new/changed area's coverage number cited as evidence the code is "well
   tested"? The global threshold is 50% (branches/functions/lines/statements,
   `jest.config.js`) — this is a floor that fails the build if crossed downward, NOT a target;
   passing at 51% is not meaningfully different from passing at 90% for signal purposes. Prefer
   asking "does this test fail if I revert the fix" (item 6) over citing a percentage.
5. Does a test assert on an error MESSAGE STRING that's likely to drift (e.g. matching a full
   sentence from `OttoChainError`/`ValidationError`) instead of the stable `ErrorCode`
   (`src/errors.ts`)? Message-string assertions rot silently when someone improves wording
   elsewhere and don't actually verify the failure mode.
6. **The "claimed but didn't" check.** For any PR that claims to fix a bug: temporarily revert
   just the fix (keep the test) and confirm the new/changed test actually goes red. A test that
   stays green with the bug reintroduced isn't testing the bug — this is the single highest-value
   check in this persona and takes under a minute per PR.
7. Dead abstractions: does the PR add a helper/wrapper with exactly one call site "for future
   reuse"? Flag it — YAGNI applies doubly to test helpers, which accumulate fastest.
8. Comments that narrate the obvious (`// increment i`) vs. comments that explain WHY (the kind
   this repo's source already models well — see the header comments in `src/schema/guards.ts` or
   `src/ottochain/morphism-lint.ts` for the target quality bar: they name the attack, not just
   the mechanism).
9. Hallucinated-API smell: does a test import a function/method that doesn't exist in the
   package's public surface, or call an SDK method with an argument shape lifted from a
   different (chain-repo, metakit-sdk) API? Cross-repo confusion is common when a model context-
   switches between `ottochain`, `ottochain-sdk`, and `metakit-sdk` in the same session.
10. Suite-name collisions: this is a Jest repo (not weaver), so the weaver `name: String`
    shadow bug doesn't apply directly — but check for `describe`/`it` blocks with generic,
    repeated titles (`describe('basic', ...)` appearing in three files) that make failures hard
    to locate from CI output alone.

## DEFECT CLASSES (examples)

- **Regenerating your own golden fixture.** The failure mode this repo is specifically guarded
  against for signed-canonical output (`signing-parity`, `sig-spec-vectors`, `canonicalize`,
  `drop-nulls`, `hash`, `binary` — the golden suite shortlist) is a test that, on a code change,
  silently updates its own expected-value fixture instead of failing. None of the current golden
  suites do this (they compare against independently-vendored vectors), but any NEW golden-style
  test must follow the same pattern: expected values live in a committed fixture the test READS,
  never one it WRITES as part of the same run.
- **Coverage-as-target thinking.** `jest.config.js` sets a 50% global floor. Treating "coverage
  went up" as a completion signal for a PR is the wrong lens — a test hitting a line without
  asserting anything meaningful about its behavior raises coverage and proves nothing. This
  repo has no mutation-testing backbone yet (unlike the chain repo's stryker4s spike) — item 6
  above (manually revert-and-check) is the interim substitute.
- **The #162-class "claimed but didn't" incident (cross-repo precedent).** A commit in the chain
  repo claimed to update the e2e harness alongside a message rename but didn't — every lifecycle
  step broke with HTTP 500, caught only by downloading CI container logs after the fact, not by
  reading the diff or trusting the PR description. Generalizes directly to this repo: never take
  a PR description's "also updated X" at face value — check that X's diff is actually present.
- **retryTimes masking a real timing bug.** `subscribe-fiber-state.test.ts` is a documented
  legitimately-flaky suite (setTimeout recursion polling) — it's in the known-flaky table with a
  reason, which is the correct way to handle unavoidable timing sensitivity. Contrast: a NEW test
  added with `retryTimes` and no table entry and no comment explaining why it's flaky is not
  following this pattern — it's hiding an unknown flake.

## OUT OF SCOPE

- Whether a signing/wire golden test's ASSERTED VALUES are chain-accurate (that's
  `signing-parity`'s or `wire-compat`'s territory — this persona checks the test's structural
  integrity, not the domain correctness of what it asserts).
- App-authoring guard/effect correctness (that's `app-authoring-safety`).
